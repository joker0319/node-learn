# 第 3 课笔记：fs 持久化，以及同步 vs 异步 IO

## 一句话结论

> 内存 = 草稿纸，文件 = 笔记本。**改完内存必须落盘**，否则进程一停什么都没了。
> 落盘用异步 IO，只有"程序启动那一刻"才可以用同步。

## 本课改了什么

第 2 课的 `todos` 只是个数组变量，进程一退出就消失。这一课加了"存储层"两个函数：

```js
loadTodos()        // 启动时：文件 → 内存
saveTodos(list)    // 每次改动后：内存 → 文件
```

四个写操作（POST / PUT / DELETE）都多了一行 `await saveTodos(todos)`。

## 核心知识点 1：同步 vs 异步 IO

`fs` 模块每个操作都有两个版本：

| 同步版 | 异步版 | 阻塞主线程吗 |
|---|---|---|
| `fs.readFileSync()` | `fsp.readFile()` | 同步：**阻塞** |
| `fs.writeFileSync()` | `fsp.writeFile()` | 异步：不阻塞 |

### 为什么同步会阻塞？

Node 是单线程执行 JS 的。`readFileSync` 期间，这段 JS 一直在等磁盘返回，**别的请求只能排队**。假设读文件要 50ms，并发 100 个请求，最后一个要等 5 秒——这就是"阻塞"的真实后果。

异步版本则是把读文件交给 libuv 的线程池，主线程立刻回去处理别的请求，文件读完了再通过回调（Promise）通知你。

### 那为什么本课的 `loadTodos` 用同步？

因为它在**服务器启动前**执行。那一刻还没有任何请求需要处理，没有人被它阻塞，代码还更简单（不用 async/await 到处传染）。

判断标准一句话：**在请求处理路径上，永远用异步；在启动初始化时，同步可以接受**。

### 一个容易忽略的坑

```js
// ❌ 这样写，接口返回时数据可能还没写完
todos.push(todo)
saveTodos(todos)          // 少了 await

return sendJSON(res, 201, todo)
```

不 `await` 的话，写文件是"后台悄悄进行"，接口先返回了。如果此时进程被 kill，数据就丢了。所以本课每个写操作都是 `await saveTodos(...)`。

## 核心知识点 2：`__dirname` 和 `path.join`

```js
const DATA_FILE = path.join(__dirname, 'data', 'todos.json')
```

- `__dirname` = **当前文件所在目录**的绝对路径（CommonJS 内置变量）
- 为什么不能写 `'./data/todos.json'`？因为相对路径的基准是**你执行 node 命令时所在的目录**。在 `~/node-learn` 下跑和进 `lessons/lesson-03` 里跑，指向的是两个不同文件——数据"凭空消失"的经典 bug。
- `path.join` 会自动处理分隔符（macOS/Linux 是 `/`，Windows 是 `\`），比手拼字符串安全。

## 核心知识点 3：id 不能重启后从 1 开始

```js
let nextId = todos.reduce((max, t) => Math.max(max, t.id), 0) + 1
```

第 2 课的 `nextId = 1` 在持久化后就出问题了：重启后新建的 todo 会拿到 id=1，和文件里已有的 id=1 撞车，后面 PUT/DELETE 会删错数据。所以重启后要从已有数据里算出最大 id 再加 1。

这也是真实数据库"自增主键"要解决的事。

## 动手作业

1. **验证持久化**：建 3 条 → `Ctrl+C` → 重启 → `curl /todos` 看数据是否还在，终端那行"已加载 3 条数据"是否对。
2. **验证 id 不撞车**：重启后新建一条，看它的 id 是不是最后一个 +1，而不是 1。
3. **把 GET 也改成异步读**（挑战）：让 `GET /todos` 每次都 `await fsp.readFile` 从磁盘现读，而不是用内存数组。想想为什么**真实项目不会这么做**，以及什么时候又必须这么做（提示：多进程部署、多个服务共享同一份文件）。

## 面试衔接

- **问：Node 是单线程，为什么能处理高并发？** 答：JS 执行是单线程，但 IO 交给 libuv 线程池 + 操作系统，主线程只负责调度回调，不等 IO。
- **问：什么时候不能用 readFileSync？** 答：在请求处理路径上，会阻塞事件循环，拖垮并发能力。
- **问：直接 writeFile 覆盖写有什么风险？** 答：写到一半进程崩溃会得到半截文件（数据损坏）。生产做法是"写临时文件 → fsync → rename 原子替换"，rename 在同一文件系统内是原子操作。
- **问：多个 Node 进程同时写同一个文件会怎样？** 答：互相覆盖，没有锁机制。这就是要用数据库而不是 JSON 文件的核心原因——**文件系统没有并发控制**。
